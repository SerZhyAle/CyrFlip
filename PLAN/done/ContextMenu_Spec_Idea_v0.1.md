# Контекстное меню над выделенным текстом — спецификация (идея, v0.1)

**Статус:** **реализовано 2026-07-27** (по запросу «пиши спецификацию и поэтапно её выполняй»).
Новые модули `MouseChord.cs`, `MouseHook.cs`, `SelectionProbe.cs`, `TextContextMenu.cs`,
`Localization.ContextMenu.cs`; правки в `WindowInterop.cs` (WH_MOUSE_LL, `MSLLHOOKSTRUCT`,
`SendMessageTimeout`, `EM_GETSEL`), `Ia2Caret.cs` (слоты vtable 5-7 + `TryGetHasSelection`),
`ClipboardHandler.cs` (`SendEditCommand` / `SendCut`), `AppConfig.cs`, `SettingsForm.cs`,
`CyrFlipContext.cs`, `Localization.cs`, `CLAUDE.md`. Тесты: `MouseChordTests`, `SelectionProbeTests`,
`TextContextMenuTests`. Сборка 0 warnings, **335 тестов зелёные** (было 300).
Ручной тест-план §9 — за пользователем: хук мыши, показ меню без фокуса и синтезированные
Ctrl+C/Ctrl+V проверяются только живьём.
**Дата:** 2026-07-27. **Автор запроса:** пользователь (SerZhyAle).

**Отклонения от этой спецификации, принятые при реализации:**

1. **Событие называется `SettingsForm.TextMenuChanged`, а не `ContextMenuChanged`.** `Control` в net48
   уже имеет событие `ContextMenuChanged` (от старого свойства `ContextMenu`), а сокрытие члена базового
   класса — CS0108, который в этом проекте в `WarningsAsErrors`.
2. **Конструктор `SettingsForm` не изменён** — вкладка говорит с контекстом одним событием, как это
   сделал переводчик: `SettingsLocalizationTests` создаёт форму рефлексией с жёстко заданным массивом
   аргументов, и любой новый параметр сломал бы тест на ровном месте.
3. **Копировать/Вырезать/Вставить отложены на один оборот цикла сообщений** (`SynchronizationContext.Post`):
   в момент клика дропдаун ещё разбирается, а синтезированный Ctrl+C адресован окну под ним.
4. **Секция настроек не гейтится общим выключателем хоткеев.** Это аккорд мыши: при снятом
   «Слушать глобальные горячие клавиши» меню продолжает работать, просто не показывает комбинаций
   (их бы всё равно не сработало).
5. **Добавлен `ForegroundActivator.cs`** — найдено первым же живым прогоном: пункт «Настройки»
   не срабатывал. Причина не в меню, а в правиле Windows: `SetForegroundWindow` даётся только процессу,
   который уже в фокусе или получил последнее событие ввода, **и отказ молчаливый** — `Form.Activate()`
   возвращается как ни в чём не бывало, окно действительно показано, но за окном пользователя. Лечится
   разделением очереди ввода с потоком активного окна (`AttachThreadInput`) на время вызова. Через него
   теперь идут все три окна, открываемые из этого меню (настройки, менеджер буфера, поиск по истории).
   Заодно **все действия меню отложены на один оборот цикла сообщений**: в момент `Click` дропдаун ещё
   разбирается и держит захват мыши.

## 1. Сценарий пользователя

1. Пользователь выделил текст в любом приложении.
2. Нажал заданный аккорд мыши (по умолчанию **Ctrl + правая кнопка**).
3. Рядом с указателем появилось меню CyrFlip:
   - первыми — **Копировать / Вырезать / Вставить**;
   - затем — то, что CyrFlip умеет сделать с выделением: строки таблицы конвертации,
     исправление регистра, перевод;
   - затем — то, что можно отсюда запустить: подменю **«Быстрый запуск»**, окно истории буфера,
     настройки.
4. Если текст **не выделен** — пункты, которым нужно выделение, **серые** (видны, но неактивны).
5. Если модуль **выключен** в настройках — его пункты **не видны вообще**.

Родное меню приложения при этом не появляется: аккорд перехвачен и проглочен.

## 2. Почему не правим меню Windows

Разобрано с пользователем перед постановкой задачи, фиксируется как принятое решение:

- **Меню современных приложений вообще не системное.** VS Code/Electron, браузеры, WPF, WinUI/UWP,
  Qt, Java рисуют его сами. `HMENU` не существует — вставлять пункт некуда.
- **Настоящее Win32-меню (`EDIT`/`RichEdit`) правится только изнутри чужого процесса**: нативная DLL
  в двух разрядностях, глобальный `WH_CALLWNDPROC` с загрузкой этой DLL в каждый процесс, перехват
  `WM_INITMENUPOPUP`. Это инъекция кода: конец «одному .exe без зависимостей», срабатывания
  антивирусов и **отказ в сертификации Microsoft Store** (MSIX не может ставить такие хуки).
  Покрытие при этом — меньшинство полей ввода.
- **TSF/TIP** (стать службой ввода текста) — отдельный продукт по объёму, нативный COM, регистрация
  языковой службы; и приложение всё равно может её меню не показать.
- **`IExplorerCommand` + sparse MSIX** — это меню Проводника для файлов, к текстовым полям
  отношения не имеет.

**Собственное меню поверх — единственный путь, который работает одинаково везде**, не требует
нативного кода и не мешает ни winget-, ни Store-сборке.

## 3. Границы фичи

**Выключена по умолчанию** (`EnableContextMenu=0`), как launcher и переводчик. Пока выключена:
низкоуровневый хук мыши **не устанавливается вообще**, ни одно событие мыши через CyrFlip не идёт,
поведение прежних сборок не меняется ни на байт.

Не входит в v0.1:
- клавиатурная навигация по меню (стрелки/Enter) — меню вызывается мышью, ей и пользуются;
- список исключений по процессам — понадобится, только если пользователь выберет `Shift+ПКМ`
  (см. §4.2); заводится отдельным этапом при необходимости;
- редактирование состава меню пользователем.

## 4. Аккорд

### 4.1 Модель

Новый тип `MouseChord` (модификаторы + кнопка), **отдельный от `Hotkey`**: у клавиатурного аккорда
обязателен VK, у мышиного — кнопка, и смешивать их в одном типе значило бы завести поле, которое в
половине случаев мусор.

Хранится в реестре **инвариантным токеном**, отображается **локализованно**:

| Токен в реестре | RU | EN |
| --- | --- | --- |
| `Ctrl+RightClick` | `Ctrl + ПКМ` | `Ctrl + Right click` |
| `Shift+RightClick` | `Shift + ПКМ` | … |
| `Alt+RightClick` | `Alt + ПКМ` | … |
| `MiddleClick` | `Средняя кнопка` | `Middle click` |
| `Ctrl+MiddleClick` | `Ctrl + средняя` | … |
| `Shift+MiddleClick` | `Shift + средняя` | … |

Выбор — **выпадающий список** из этих шести, а не диалог захвата. Причина: правая кнопка **обязана**
идти с модификатором (иначе мы съедаем контекстное меню всей системы), а список это гарантирует
конструктивно, без валидации и без возможности прострелить себе ногу.

Нераспознанный токен → дефолт `Ctrl+RightClick` (та же дисциплина, что у `Hotkey.Parse`).

### 4.2 Почему дефолт — Ctrl+ПКМ, а не Shift+ПКМ

`Shift + ПКМ` в Проводнике и на рабочем столе — это «расширенное меню» Windows («Копировать как
путь», «Запуск от имени другого пользователя»). Перехватив его глобально, мы отберём у пользователя
живую функцию оболочки. `Ctrl + ПКМ` в Windows не занят ничем.

Средняя кнопка занята автоскроллом и «открыть в новой вкладке» — как дефолт рискованна, как явно
выбранная опция нормальна.

### 4.3 Конфликты

Мышиные аккорды живут в **отдельном пространстве** от клавиатурных: пересечься с `Ctrl+Shift+F12`
они не могут. Существующая 4-сторонняя проверка (`SettingsForm.ClashingCyrFlipAction`) не трогается.

## 5. Перехват (`MouseHook.cs`)

`SetWindowsHookEx(WH_MOUSE_LL)`, тот же файл-пример дисциплины — `KeyboardHook.cs`.

### 5.1 Колбэк

```
nCode < 0                       -> CallNextHookEx
wParam не из четвёрки наших     -> CallNextHookEx     (сюда уходит каждый WM_MOUSEMOVE)
LLMHF_INJECTED                  -> CallNextHookEx
down/dblclk нашей кнопки + модификаторы совпали
                                -> _swallowUp = true; ChordPressed(pt); return 1
up нашей кнопки при _swallowUp  -> _swallowUp = false; ChordReleased(pt); return 1
иначе                           -> CallNextHookEx
```

Пять правил, ни одного вызова наружу на обычном движении мыши.

### 5.2 Пять вещей, которые здесь легко сделать неправильно

1. **`WH_MOUSE_LL` получает каждое движение указателя** — до 1000 событий в секунду с игровой мышью.
   Колбэк = сравнение `wParam` и немедленный выход. Никаких `Marshal.PtrToStructure`, пока не
   доказано, что событие наше (структура читается только ради координат, уже внутри ветки).
2. **Пауза GC на потоке хука тормозит мышь во всей системе.** Windows ждёт нас до
   `LowLevelHooksTimeout` (по умолчанию 300 мс) и потом молча снимает хук. Отсюда §3: пока фича
   выключена, хука нет вовсе.
3. **Меню нельзя показывать из колбэка.** Это запустило бы чужой цикл сообщений внутри хука. Событие
   постится в UI-поток (`SynchronizationContext.Post`), колбэк возвращает `1` немедленно.
4. **Глотать нужно и `down`, и `up`, и `dblclk`.** Большинство приложений показывают меню по
   `WM_CONTEXTMENU`, который приходит **после** отпускания; одинокий `up` вызовет чужое меню поверх
   нашего. Быстрый второй клик приходит как `WM_RBUTTONDBLCLK`, а не `DOWN`.
5. **Модификатор может быть отпущен раньше кнопки.** Поэтому `up` глотается по флагу `_swallowUp`,
   а не по повторной проверке модификаторов.

### 5.3 Известное ограничение

UIPI: неповышенный процесс не получает событий от окон, запущенных от администратора. Там аккорд
отработает штатно — родное меню приложения. То же ограничение, что у нынешних клавиатурных аккордов;
в интерфейсе не обещаем обратного.

## 6. Определение выделения (`SelectionProbe.cs`)

Самое трудное место. Дешёвого универсального API нет.

### 6.1 Источники, по порядку

| # | Источник | Покрывает | Цена |
| --- | --- | --- | --- |
| 1 | `EM_GETSEL` через `SendMessageTimeout` на сфокусированный HWND | классические `Edit`/`RichEdit` (Блокнот, поля диалогов) | микросекунды |
| 2 | IAccessible2 `IAccessibleText.nSelections` + `selection(0)` | Chromium/Electron (VS Code, браузеры) | десятки мс |
| 3 | UIA `TextPattern.GetSelection()` — невырожденный диапазон | WinUI/UWP/WPF | десятки мс |

Первый источник **гейтится по имени класса** (`Edit`, `RichEdit*`): `EM_GETSEL`, посланный не-эдиту,
уходит в `DefWindowProc` и вернёт 0 — то есть **ложное «нет выделения»**, а это ровно тот баг,
который пользователь видит глазами. Класс не подошёл → сразу источник 2.

Источники 2 и 3 — те же модули, что уже носят каретку (`Ia2Caret`, managed UIA в `CaretOverlay`);
`IAccessibleText` дополняется двумя слотами vtable (`nSelections` = 5, `selection` = 7 — порядок
слотов несущий, см. «COM vtable gotchas» в CLAUDE.md).

### 6.2 Три состояния, а не два

```csharp
enum SelectionState { Present, Absent, Unknown }
```

`Unknown` (ни один источник не ответил — консоль, часть Qt/Java) трактуется как **`Present`**:
пункты активны. Серый пункт при живом выделении — баг, который пользователь замечает сразу;
активный пункт, который ничего не сделал, — уже штатное поведение всех наших операций
(«нет выделения → тихий no-op», спека §5.3 основной спецификации).

### 6.3 Когда опрашивать

Опрос стартует на **нажатии** аккорда, меню строится на **отпускании**. Пользователь держит кнопку
80-150 мс — этого хватает, чтобы ответ пришёл к моменту отрисовки, **без единой миллисекунды
искусственной задержки**. Ожидание на показе ограничено 150 мс от нажатия; не успели → `Unknown`.

Опрос идёт на выделенном **MTA**-потоке (COM), создаваемом на каждый вызов: событие редкое
(клик пользователя), а долгоживущий воркер с очередью здесь — лишняя машинерия.

### 6.4 Чего мы принципиально не делаем

**Не «пробуем» выделение синтетическим Ctrl+C.** Это положило бы текст в буфер обмена только ради
построения меню — и история буфера записала бы его как обычную копию (модуль истории слушает
`AddClipboardFormatListener` и по замыслу не теряет ничего). Загрязнять историю ради серости пункта
недопустимо.

## 7. Меню (`TextContextMenu.cs`)

### 7.1 Форма

Обычный `ContextMenuStrip`. Ключевой факт: `ToolStripDropDown.ShowWithoutActivation` в WinForms
уже `true` — выпадающее меню **не забирает фокус**. Значит:

- целевое окно остаётся активным, и **выделение в нём остаётся выделением**;
- средний/правый клик, в отличие от левого, не сдвигает каретку и не сбрасывает выделение;
- последующий синтезированный `Ctrl+C`/`Ctrl+V` попадает туда же, куда попал бы у пользователя.

Даром получаем субменю, иконки, DPI-масштабирование, `RightToLeft` для арабского и урду.

**Закрытие по клику мимо.** Дропдаун без активного владельца в норме не закрывается с первого
внешнего клика (та же болячка, что у трей-меню — ср. `SetForegroundWindow` в
`LauncherTaskbarWindow.ShowMenu`). Здесь она лечится бесплатно: **мышиный хук уже стоит**, мы видим
следующий клик первыми и закрываем меню сами. Вызывать `SetForegroundWindow` **нельзя** — это
отобрало бы фокус у поля ввода, ради сохранения которого всё и затевалось.

### 7.2 Состав

```
Копировать                 Ctrl+C      [нужно выделение]
Вырезать                   Ctrl+X      [нужно выделение]
Вставить                   Ctrl+V      [нужен непустой буфер]
────────────────
EN ⇄ RU                    Ctrl+Shift+F12   [нужно выделение]   ← по строке на каждую
UK ⇄ EN                    Alt+Shift+F12    [нужно выделение]      включённую строку таблицы
Исправить регистр          Ctrl+Shift+F11   [нужно выделение]
Перевести на English       Ctrl+Shift+F9    [нужно выделение]   ← только при EnableTranslate
────────────────
Быстрый запуск ▸                           ← только при EnableScenarioLauncher
Менеджер буфера                            ← только при EnableClipboardHistory
────────────────
Настройки...
```

- Строки конвертации и перевода берутся из живых таблиц, а не зашиты: подпись — та же, что в
  настройках и в тултипе трея (`WorldLayouts.LabelForKlid` / `TranslationLanguages.Label`),
  справа — аккорд строки (`ShortcutKeyDisplayString`), чтобы меню заодно **обучало хоткеям**.
- Подменю «Быстрый запуск» строится **тем же `LauncherTrayMenu.Fill`**, что и трей и кнопка на
  панели задач: три поверхности из одной функции не могут разъехаться.
- «Менеджер буфера» — один пункт, открывающий существующее окно истории (решение пользователя:
  вставки последних записей прямо из меню в v0.1 нет).
- Выключенные строки таблиц (`Enabled=false`) в меню не попадают вовсе — как и не срабатывают их
  аккорды.

### 7.3 Правила видимости и серости

| Пункт | Не виден, когда | Серый, когда |
| --- | --- | --- |
| Копировать / Вырезать | никогда | `SelectionState.Absent` |
| Вставить | никогда | в буфере нет текста |
| Строки конвертации | таблица пуста / строка выключена | `Absent` |
| Исправить регистр | никогда | `Absent` |
| Строки перевода | `EnableTranslate=0` | `Absent` |
| Быстрый запуск | `EnableScenarioLauncher=0` | никогда |
| Менеджер буфера | `EnableClipboardHistory=0` | никогда |
| Настройки | никогда | никогда |

Разделители не должны «повисать»: пустая группа убирает и свой разделитель. Это чистая функция от
состояния — она и есть главный объект юнит-тестов (§9).

### 7.4 Действия

- **Копировать / Вырезать / Вставить** — синтезированные `Ctrl+C` / `Ctrl+X` / `Ctrl+V` в активное
  окно, через тот же конвейер `SendInput`, что и флип: сначала отпускаются модификаторы, которые
  испортили бы аккорд, потом восстанавливаются те, что пользователь физически держит
  (`HeldModifiers`). Клипборд при этом **не подменяется и не восстанавливается** — пользователь
  просил копировать, значит копия должна остаться в буфере (и в истории).
- **Конвертация / регистр / перевод** — ровно те же вызовы, что из хука
  (`OnLayoutConversionHotkeyPressed`, `OnCaseHotkeyPressed`, `OnTranslateHotkeyPressed`), со всеми
  их гарантиями: единый `_busy`, счётчики, трёхфазность перевода. Никакого второго пути исполнения.
- **Запуск сценария** — `LauncherExecution.Launch`, как из трея.

## 8. Конфигурация

| Значение реестра | Тип | По умолчанию | Описание |
| --- | --- | --- | --- |
| `EnableContextMenu` | `REG_DWORD` | `0` | 1 = меню включено (хук мыши установлен). 0 = хук не ставится вовсе |
| `ContextMenuChord` | `REG_SZ` | `Ctrl+RightClick` | Аккорд вызова; нераспознанный токен = дефолт |

Место в настройках — **секция «Контекстное меню» на вкладке «Горячие клавиши»**: это аккорд, а не
отдельная подсистема, и десятая вкладка ради двух контролов не нужна. Секция = чекбокс + выпадающий
список + строка описания, включая честное предупреждение для вариантов со средней кнопкой и
`Shift+ПКМ`.

Пункта в трее фича не получает (как launcher и переводчик, включатель живёт в настройках).

## 9. Тесты

**Юнит (`dotnet test`, обязательны):**

- `MouseChordTests` — разбор всех шести токенов, мусорный токен → дефолт, round-trip
  `Parse`/`ToString`, совпадение с событием (кнопка + точный набор модификаторов, «не больше и не
  меньше», как `KeyboardHook.Matches`).
- `TextContextMenuTests` — построение меню как чистая функция от состояния:
  - полный набор при `Present` и всех включённых модулях;
  - при `Absent` пункты выделения серые, но **присутствуют**;
  - при `Unknown` пункты активны (fail-open — отдельный тест, потому что это неочевидное решение);
  - выключенные модули не дают ни пунктов, ни висящих разделителей;
  - «Вставить» серая при пустом буфере и активная при непустом, независимо от выделения;
  - **повторные перестроения** — как в `LauncherTrayMenuTests`: первый Rebuild не может упасть,
    ловит только второй (`ToolStripItem.Dispose` удаляет элемент из коллекции владельца);
  - каждый пункт вызывает своё действие (проверка захвата в замыкании по индексу).
- `SelectionProbeTests` — решающая логика через подменяемый seam источников: первый определённый
  ответ побеждает, `Absent` от источника 1 на не-эдит-классе не запрашивается вовсе, все
  `Unknown` → `Unknown`, таймаут → `Unknown`.
- `SettingsLocalizationTests` / `DialogLayoutTests` — существующие гарантии подхватят новые строки
  автоматически (перевод на все 13 языков обязателен, кириллица в нерусской сборке = провал).

**Ручная проверка (interop, вне CI):**

1. Ctrl+ПКМ по выделенному тексту в Блокноте, VS Code (чат и редактор), Chrome, Word, поле поиска
   Проводника — меню появляется, родное не появляется.
2. Ctrl+ПКМ без выделения — пункты выделения серые.
3. Обычный ПКМ везде работает как раньше; автоскролл средней кнопкой цел.
4. «Копировать» из меню кладёт текст в буфер и в историю; «Вставить» вставляет.
5. Конвертация/регистр/перевод из меню дают тот же результат, что аккорд с клавиатуры.
6. Клик мимо меню закрывает его с первого раза.
7. Выключение фичи в настройках — хук снят, аккорд снова доходит до приложения (проверить, что
   `Ctrl+ПКМ` в Проводнике опять открывает родное меню).
8. Окно с правами администратора — аккорд не перехвачен, родное меню, приложение не падает.
