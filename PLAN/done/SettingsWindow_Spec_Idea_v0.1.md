# Спецификация-идея v0.1
## Окно настроек для CyrFlip

> Концепт дополнительной UI-поверхности для текущего tray-приложения `CyrFlip`.
> Статус: MVP реализован. Разделы и редкие будущие настройки продолжают развиваться.

---

## 1. Идея

Сейчас `CyrFlip` живёт почти целиком в `tray`-меню: это удобно для быстрых переключателей, но по мере роста функций меню становится длинным, перегруженным и плохо объясняет смысл каждой опции.

Идея: добавить **отдельное окно настроек**, при этом:

- быстрые и часто используемые галочки **остаются в трее**;
- в окне настроек эти же опции можно **повторить**;
- там же можно разместить **более редкие настройки**, которым не место в tray-меню;
- рядом с каждой настройкой можно дать **человеческое объяснение**, что именно она делает и зачем нужна.

Отдельно остаётся давно напрашивающееся действие:

- **двойной клик по иконке в трее** открывает это окно настроек.

---

## 2. Зачем это нужно

Tray-меню хорошо работает как:

- быстрый доступ;
- включить/выключить фичу в один клик;
- показать статус;
- вызвать 1-2 действия.

Но tray-меню плохо подходит для:

- длинных списков опций;
- взаимосвязанных настроек;
- подробных пояснений;
- настройки горячих клавиш в одном месте;
- будущих экспериментальных функций.

Окно настроек решает эту проблему без потери текущего удобства:

- быстрые действия остаются быстрыми;
- сложные настройки получают нормальный дом.

---

## 3. Главный UX-принцип

Нужны **две поверхности управления**, а не замена одной другой:

### Tray

Оставить в трее только то, что действительно полезно переключать на ходу:

- включить/выключить индикатор на курсоре;
- включить/выключить overlay у каретки;
- быстрый доступ к hotkey;
- запуск диагностики;
- запуск с Windows;
- выход.

### Окно настроек

Сделать его местом для:

- полного списка настроек;
- пояснений;
- более редких и продвинутых опций;
- будущих функций, которые перегрузили бы tray-меню.

Идея в том, что tray отвечает на вопрос:

**"Как быстро переключить что-то прямо сейчас?"**

А окно настроек отвечает на вопрос:

**"Как вообще настроить CyrFlip под себя?"**

---

## 4. Пользовательские сценарии

### Сценарий 1. Быстрое переключение

Пользователь хочет временно выключить маркер у каретки.

1. Правый клик по tray-иконке.
2. Снимает галочку `Caret overlay`.
3. Продолжает работу.

Для этого окно настроек не нужно.

### Сценарий 2. Спокойная настройка

Пользователь хочет понять:

- чем отличаются индикатор на курсоре и у каретки;
- что делает `dot mode`;
- зачем нужна смена языка после flip;
- какие hotkey уже настроены.

1. Двойной клик по tray-иконке.
2. Открывается окно настроек.
3. Пользователь читает пояснения и меняет параметры в одном месте.

### Сценарий 3. Рост приложения

Когда появятся новые функции, например:

- clipboard history;
- дополнительные режимы отображения;
- privacy-настройки;
- экспериментальные функции;

их можно будет добавить в окно настроек, не превращая tray-меню в длинную простыню.

---

## 5. Функциональные требования

### 5.1 Открытие окна

Окно настроек должно открываться:

- по пункту `Settings...` в tray-меню;
- по **двойному клику** на tray-иконке;
- опционально позже по отдельной горячей клавише.

### 5.2 Поведение окна

Окно:

- не должно запускать второй экземпляр;
- если уже открыто, повторный вызов просто активирует и показывает существующее окно;
- может закрываться крестиком без завершения приложения;
- при закрытии просто скрывается, а `CyrFlip` продолжает жить в трее;
- не должно появляться в неожиданные моменты само по себе.

### 5.3 Сохранение настроек

Все изменения в окне используют тот же механизм конфигурации, что и tray:

- изменения применяются сразу или после `Apply`/`OK`;
- состояние синхронизировано между tray-меню и окном;
- если пользователь поменял галочку в трее, окно тоже показывает актуальное состояние;
- если пользователь поменял опцию в окне, tray тоже обновляется.

## 6. Что должно быть в окне настроек

### 6.1 Базовые настройки

В окне нужно повторить уже существующие основные опции:

- включить индикатор раскладки на курсоре;
- включить overlay у каретки;
- включить `dot mode`;
- менять язык после `flip`;
- переключать `CapsLock` после case-flip;
- запускать программу вместе с Windows.

### 6.2 Настройка горячих клавиш

Сейчас hotkey настраиваются через отдельные диалоги. В окне настроек можно собрать это в один блок:

- hotkey для `Flip EN ⇄ RU`;
- hotkey для `Flip case`;
- позже hotkey для окна истории буфера;
- позже hotkey для открытия окна настроек.

Для каждой клавиши полезно показывать:

- текущее значение;
- кнопку `Change...`;
- краткое описание действия.

### 6.3 Пояснения рядом с опциями

Это одна из главных причин вообще делать окно.

Примеры объяснений:

- `Cursor indicator`
  - Показывает текущую раскладку прямо на текстовом курсоре мыши (I-beam).

- `Caret overlay`
  - Показывает маленький маркер рядом с мигающей кареткой там, где вы печатаете.

- `Dot mode`
  - Вместо букв EN/RU/UK показывает компактную цветную точку рядом с кареткой.

- `Change language after flip`
  - После исправления текста переключает раскладку, чтобы вы могли сразу продолжать печатать в правильном языке.

- `Flip CapsLock after case-flip`
  - После исправления регистра синхронизирует состояние физической клавиши CapsLock с результатом.

### 6.4 Настройки, которых не должно быть в трее

Часть опций логично держать только в окне:

- подробные пояснения;
- экспериментальные функции;
- privacy-настройки;
- лимиты и тонкая настройка будущего clipboard history;
- диагностические режимы;
- поведение уведомлений;
- дополнительные визуальные настройки.

Именно такие опции и делают окно оправданным.

## 7. Предлагаемая структура окна

Лучше не делать просто длинную вертикальную колонку галочек. Более устойчивый вариант:

### Вариант A. Вкладки

- `General`
- `Indicators`
- `Hotkeys`
- `Clipboard`
- `Advanced`
- `About`

Это масштабируется лучше всего по мере роста приложения.

### Вариант B. Левая навигация + правая панель

- слева список разделов;
- справа содержимое выбранного раздела;
- внизу кнопки `OK`, `Cancel`, `Apply`.

По UX это может быть даже лучше вкладок, если настроек станет много.

Для `CyrFlip` наиболее реалистичный старт:

- обычный WinForms `Form`;
- `TabControl` или простая секционная форма;
- без лишней визуальной сложности.

## 8. Предлагаемые разделы

### General

- запуск с Windows;
- язык интерфейса в будущем, если он появится;
- поведение двойного клика по tray;
- показывать ли окно настроек при первом запуске.

### Indicators

- cursor indicator;
- caret overlay;
- dot mode;
- размер курсора;
- будущие цвета/прозрачность/позиция overlay.

### Hotkeys

- hotkey flip;
- hotkey case-flip;
- будущие hotkey для clipboard history;
- предупреждения о конфликтах.

### Clipboard

Раздел появляется вместе с clipboard history (см. [ClipboardHistoryTray_Spec_Idea_v0.1.md](ClipboardHistoryTray_Spec_Idea_v0.1.md)). Опции:

- включить историю (opt-in, по умолчанию выключено);
- hotkey показать/скрыть окно истории (по умолчанию `Ctrl+Shift+F10`);
- **прозрачность окна истории**: уровень от 30% до 100% с немедленным предпросмотром; значение сохраняется в `HKCU\Software\CyrFlip` и применяется к плавающему окну без перезапуска;
- `Pause history capture` - временно не захватывать;
- **`Показывать окно менеджера буфера на старте`** — отдельная опция от включения истории: позволяет продолжать захват и хранение истории, не оставляя окно на экране после каждого запуска;
- **операции над историей** (модель хранения - append-only лог, храним всё):
  - **`Очистить историю`** - полностью стереть память и файл на диске;
  - **`Обрезать историю до 100`** - оставить только 100 самых свежих записей (компакция лога);
- сохранять ли RTF (Этап 2);
- privacy-предупреждение: история пишется на диск в зашифрованном (DPAPI) виде, но всё равно содержит пароли/личное - объяснить это человеческим языком прямо в разделе.

> Почему усечение и очистка живут здесь, а не в трее: это редкие, потенциально разрушительные действия - им место в окне настроек с пояснением, а не в быстром tray-меню (там остаются только `Show history` / `Pause` / `Clear`).

### Advanced

- диагностика каретки;
- экспериментальные функции;
- отладочные или технические параметры.

### About

- версия;
- краткое описание;
- ссылки на README / GitHub / лицензию;
- статус конфигурации.

## 9. Двойной клик по tray-иконке

Сейчас это хорошая незанятая точка входа.

Рекомендуемое поведение:

- **двойной левый клик** по tray-иконке открывает окно настроек;
- если окно уже открыто и скрыто за другими окнами, оно выводится на передний план;
- если окно свернуто, оно восстанавливается;
- если окно уже активно, повторный двойной клик ничего не ломает.

Почему это правильно:

- пользователь интуитивно ожидает, что двойной клик по tray-утилите откроет её "главное окно";
- у `CyrFlip` сейчас такого главного окна фактически нет;
- окно настроек естественно становится этой основной UI-точкой.

Опционально потом можно добавить настройку:

- `Double-click action`
  - Open Settings
  - Toggle Caret Overlay
  - Show Clipboard History

Но для MVP лучше не усложнять и просто привязать двойной клик к `Settings`.

## 10. Архитектура в рамках текущего проекта

### 10.1 Возможные новые компоненты

- `SettingsForm.cs`
  - главное окно настроек;
  - вкладки/секции;
  - пояснения к опциям;
  - управление hotkey и feature toggles.

- `SettingsPresenter.cs` или аналогичная прослойка
  - синхронизация UI с `AppConfig`;
  - применение изменений;
  - обновление `CyrFlipContext`.

- обновления в `CyrFlipContext.cs`
  - новый пункт `Settings...` в tray-меню;
  - обработчик двойного клика по `NotifyIcon`;
  - единый метод `ShowSettings()`;
  - синхронизация состояний между tray и окном.

### 10.2 Связь с AppConfig

Окно не должно вводить второй источник истины.

Правильная модель:

- `AppConfig` остаётся центральным хранилищем;
- tray и `SettingsForm` просто две UI-поверхности над одними и теми же данными;
- применение настроек идёт через существующую логику `CyrFlipContext`.

## 11. Синхронизация tray и окна

Это один из самых важных моментов реализации.

Нужно гарантировать:

- если галочка изменилась в трее, окно сразу или при следующем открытии показывает то же состояние;
- если hotkey изменён в окне, заголовки и подсказки в tray обновляются;
- если Windows управляет autostart через StartupTask, окно должно показывать это корректно так же, как и tray.

Иначе пользователь получит два несогласованных интерфейса, и доверие к настройкам быстро сломается.

## 12. MVP

Минимально полезная версия окна настроек:

1. Пункт `Settings...` в tray-меню.
2. Двойной клик по tray-иконке открывает окно.
3. Окно повторяет текущие основные toggles.
4. В окне есть блок hotkey-настроек.
5. У каждой опции есть краткое понятное описание.
6. Окно закрывается в скрытие, а не завершает приложение.
7. Tray и окно синхронизированы по состоянию.

## 14. Риски и компромиссы

- Если просто продублировать tray-меню один в один, окно не даст реальной пользы.
- Если убрать слишком много из tray, пострадает скорость доступа.
- Если добавить слишком подробный UI слишком рано, маленькая утилита начнёт выглядеть тяжелее, чем она есть.
- Если не продумать синхронизацию, настройки в разных местах начнут расходиться.
- Если окно будет модальным или навязчивым, это сломает лёгкий характер `CyrFlip`.

Поэтому важно держать баланс:

- tray для быстрых действий;
- окно для понимания и полного контроля.

---

## 15. Почему это подходит CyrFlip

Потому что продукт уже вырос из состояния "одна-две галочки в меню", но ещё не должен превращаться в тяжёлое приложение с главным окном.

Окно настроек:

- делает продукт понятнее;
- подготавливает архитектуру к новым функциям;
- разгружает tray;
- создаёт естественное действие для двойного клика по иконке.

Это не меняет философию `CyrFlip` как tray-first утилиты, а только добавляет ей более дружелюбную и масштабируемую точку настройки.

---

## 16. Итог

Лучший путь для `CyrFlip` - **не убирать управление из трея, а дополнить его окном настроек**.

Tray остаётся местом для быстрых переключений.
Окно настроек становится местом, где:

- видны все параметры;
- есть объяснения человеческим языком;
- можно разместить редкие и будущие функции;
- двойной клик по tray наконец получает понятную роль.

Если делать это поэтапно, то даже MVP уже даст заметное улучшение UX без изменения основной философии приложения.
