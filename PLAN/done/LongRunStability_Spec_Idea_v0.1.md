# Стабильность при долгой работе — спецификация исправлений (идея, v0.1)

**Статус:** **реализовано 2026-07-30** (по запросу «выполни эту спецификацию»). Все девять работ
§1 сделаны, `dotnet build` warning-free в Debug и Release, `dotnet test` — **415 тестов зелёные**
(было 391; +24 новых: `ClipboardHistoryOrderTests` 11, `DiagnosticLogTests` 7,
`ClipboardBackupTests` 6). `Test-LongRun.ps1` проверен коротким прогоном против живого экземпляра:
5 сэмплов, GDI 91→91, USER 51→51, PASS. Ручные проверки §3 (скриншот/файлы переживают флип) и
часовой прогон — за пользователем.
**Дата:** 2026-07-30. **Источник:** полный аудит кода на предмет долгой фоновой работы
(утечки памяти, зависания, потери данных), проведённый по запросу пользователя 2026-07-30.
**Автор запроса:** пользователь (SerZhyAle).

**Отклонения от плана, принятые при реализации:**

- **§10 — проверку живости хука нельзя автоматизировать.** План предполагал, что скрипт сам
  пошлёт аккорд истории. Это невозможно по устройству самого приложения: `KeyboardHook` игнорирует
  события с `LLKHF_INJECTED` (иначе его собственный `SendInput` входил бы в хук рекурсивно), так
  что синтезированный `Ctrl+Shift+F10` не доказал бы ничего. Скрипт вместо этого **просит человека**
  нажать аккорд в конце прогона и смотрит, появилось ли окно — та же проверка, но честная.
- **§7 — ротация переписывает файл на месте**, а не через временный файл с заменой. Замена
  означает удаление, а файл, открытый другим процессом, удалить нельзя — и это ровно тот случай,
  который важен: `SupportBundle` читает эти самые логи, собирая архив. Поймано тестом
  `A_log_held_open_for_writing_is_still_rotated`, который на первой версии падал.
- **§6 — установка хука перенесена ниже захвата `_ui`.** Раз все события хука теперь постятся в
  `_ui`, аккорд, нажатый между `Install` и захватом контекста, был бы проглочен и потерян.
- **§5 — вместо шести операций реализованы три** (`Add` / `Update` / `Remove`): touch, pin и unpin
  несут одни и те же два поля, поэтому один `Update(entry, createdAt, pinned)` покрывает все три и
  не может оставить запись перемещённой наполовину.

**Итог аудита в одну строку:** классических утечек нет (GDI, COM RCW, хэндлы, потоки и таймеры
освобождаются дисциплинированно), но есть один системный риск отказа — молчаливое снятие
low-level-хуков системой без переустановки, — один сценарий потери данных пользователя
(не-текстовый буфер обмена при флипе) и несколько источников медленной деградации.

**Правило отбора для этой спеки:** входит всё **существенное** — и всё **несущественное, но
простое**. Сложное-и-несущественное честно вынесено в §11 «Не входит».

## 2. Сторож LL-хуков (№1)

### Проблема

Колбэки `WH_KEYBOARD_LL` / `WH_MOUSE_LL` вызываются на потоке, который их установил, — на UI-потоке
трея. Windows ждёт ответа не дольше `LowLevelHooksTimeout` (~200–300 мс) и, начиная с Windows 7,
**после превышений молча снимает хук** — приложению об этом не сообщается никак. Сам колбэк у нас
быстрый; таймаут набирается занятостью *всего потока* в момент прихода клавиши:

- `SelectionProbe.Collect` — до 150 мс на UI-потоке (заложено сознательно);
- `Win32Clipboard.OpenWithRetry` — до 180 мс ретраев внутри `ClipboardHistoryService.Capture`
  (WndProc, UI-поток) на каждое системное копирование, если чужой процесс держит буфер;
- `RunLauncherScenario` → `Process.Start` на UI-потоке (антивирус/сетевой путь = секунды);
- паузы GC 2-го поколения, растущие вместе с безлимитной историей.

Симптом у пользователя: «после долгой работы хоткеи перестали работать» (вместе с контекстным
меню и Esc-отменой перевода) — до перезапуска приложения.

### Решение

1. `KeyboardHook.Reinstall()` и `MouseHook.Reinstall()`: если хук был установлен —
   `UnhookWindowsHookEx` + `SetWindowsHookEx` тем же `_proc` (делегат уже удерживается полем).
   Метод обязан вызываться с потока-владельца.
2. В `CyrFlipContext` — `System.Windows.Forms.Timer` с интервалом **60 с** (тик на UI-потоке,
   то есть на нужном потоке автоматически):
   - `_hook.Reinstall()` — всегда (клавиатурный хук живёт всю сессию);
   - `_mouseHook.Reinstall()` — только пока `Installed` (фича контекстного меню включена).
3. Границы корректности:
   - **не** переустанавливать мышиный хук, пока `_swallowUp == true` (аккорд зажат: потеря флага
     отпустила бы «up» в чужое окно) — `Reinstall` мышиного хука при взведённом флаге просто
     пропускает цикл;
   - переустановка клавиатурного хука между down и up аккорда безвредна: состояние аккорда
     хранится не в хуке, а в `GetAsyncKeyState`.
4. Неудача `SetWindowsHookEx` (вернул 0): не падать, повторить на следующем тике; после
   **3 неудач подряд** — один балун «Не удалось восстановить перехват клавиатуры — хоткеи могут
   не работать» (и продолжать попытки). Это ровно та честность, которой нет у молчаливого снятия.

**Отклонённая альтернатива:** детектор-«пульс» (сравнивать активность клавиатуры по
`GetAsyncKeyState` со счётчиком вызовов колбэка и переустанавливать только по расхождению).
Сложнее, порождает ложные срабатывания, а безусловная переустановка стоит микросекунды в минуту.

### Приёмка

- Обычная работа не меняется: аккорды срабатывают, автоповтор блокируется, `Dispose` снимает хук.
- Проверка живости — в `Test-LongRun.ps1` (§10): периодическая отправка аккорда истории и
  контроль, что окно истории появляется/скрывается (= хук жив и глотает клавишу).
- Юнит-тестов нет (чистый interop); вся логика метода — 6 строк.

## 3. Бэкап не-текстового буфера обмена (№2)

### Проблема

`ClipboardHandler.BackupClipboard` сохраняет только `CF_UNICODETEXT`, а `Win32Clipboard.TrySetText`
начинает с `EmptyClipboard()`. Пользователь скопировал скриншот или файлы → поправил слово
хоткеем → **картинка/файлы из буфера пропали безвозвратно**: `HadText == false`, восстанавливать
нечего. При ежедневном использовании это самая ощутимая «потеря» из найденных.

### Решение (v1 — allow-list из трёх форматов)

Бэкапить и восстанавливать **три формата, закрывающих практически все пользовательские потери**:

| Формат | Что это | Почему достаточно |
| --- | --- | --- |
| `CF_UNICODETEXT` | текст | уже есть |
| `CF_DIB` (8) | картинка | Windows сама синтезирует `CF_BITMAP`/`CF_DIBV5` из `CF_DIB` и обратно — восстановленный DIB снова вставляется everywhere |
| `CF_HDROP` (15) | список файлов | блок `DROPFILES` самодостаточен (смещение + double-null список) — побайтовая копия глобального блока восстанавливается verbatim |

Механика — в `Win32Clipboard`, тем же raw-Win32 стилем:

```csharp
// чтение:  GetClipboardData(fmt) → GlobalLock → копия GlobalSize(h) байт → GlobalUnlock
public static bool TryGetBytes(uint format, out byte[]? data);
// запись:  GlobalAlloc(GMEM_MOVEABLE) → копия → SetClipboardData(fmt, h)
//          (владение уходит системе только при успехе — как в TrySetText)
public static bool TrySetBytes(uint format, byte[] data);
```

`ClipboardBackup` расширяется полями `byte[]? Dib` и `byte[]? Drop`; `BackupClipboard` снимает
все три формата за **одно** открытие буфера; `RestoreClipboard`, если есть что вернуть, делает
одно открытие: `EmptyClipboard` → `SetClipboardData` для каждого сохранённого формата.

Ограничения (осознанные):

- **Кап размера DIB: 64 МБ.** Больше — формат не бэкапится (сегодняшнее поведение), чтобы флип
  не копировал полугигабайтный скан туда-обратно. Текст и HDROP капа не требуют.
- `GetClipboardData` на delayed-rendered формате принудит владельца отрисовать данные — штатно.
- Восстанавливаются только сохранённые форматы: RTF/HTML-спутники текстовой копии в v1
  по-прежнему теряются (текст — главный носитель; полная переборка всех HGLOBAL-форматов — §11).

### Приёмка / тесты

- Юнит: round-trip хелперов не тестируется без буфера; чистой логики здесь нет — проверка ручная.
- Ручной сценарий (войдёт в README `tools/uitest`): PrintScreen → флип слова хоткеем →
  Ctrl+V в Paint вставляет **исходный скриншот**; копия файла в проводнике → флип → Ctrl+V
  в папке вставляет файл. Скриптовая половина: probe `IsClipboardFormatAvailable(CF_DIB/CF_HDROP)`
  до и после флипа.

## 4. Сохранение позиции окна истории (№3)

### Проблема

`ClipboardHistoryWindow`: `Move += (_, _) => { if (Visible) SaveBounds(); }`, а `SaveBounds`
зовёт полный `AppConfig.Save()` — ~45 значений реестра плюс **две JSON-сериализации таблиц
профилей** — на каждое событие Move, которых при перетаскивании десятки в секунду.

### Решение

- Убрать `Move`-подписку.
- Перетаскивание своё (borderless, кастомный drag): сохранять один раз в `MouseUp`, если
  `_dragging` был взведён: `if (_dragging) { _dragging = false; SaveBounds(); }`.
- `ResizeEnd → SaveBounds()` остаётся как есть (уже одно событие на жест).

Окно перевода (`TranslationResultWindow`) уже сохраняется правильно — только `ResizeEnd`,
его не трогаем.

### Приёмка

Перетащить окно истории при запущенном Process Monitor (или просто по счётчику вызовов в
отладке): за жест — **одна** запись в реестр. Позиция переживает перезапуск (как раньше).

## 5. История буфера: O(1)-дисциплина и `_suppressNext` (№4)

Безлимитность истории — принятое решение (2026-07-26), **не пересматривается**. Но само решение
обязывает: «ничто не должно стоить O(истории) на копирование или перерисовку». Два места
нарушают это обязательство, третье — маленький баг рядом.

### 5.1 `SetCurrent` — O(n) на каждое копирование

Обходит все записи, чтобы снять флажок `IsCurrent`. Замена: поле `_current`
(ссылка на текущую запись); `SetCurrent` снимает флаг у старой и ставит новой — O(1).

### 5.2 Пересортировка `Entries` — O(n·log n) на каждое копирование

`_ordered` сбрасывается в `RaiseChanged` и пересобирается полным
`OrderByDescending(IsPinned).ThenByDescending(CreatedAt)` при следующей отрисовке — то есть
фактически на каждый Ctrl+C, на UI-потоке, с делегатными сравнениями и аллокацией нового списка.

Замена — **инкрементальное поддержание порядка** в том же `List<>`:

- инвариант списка: закреплённые (по `CreatedAt` убыв.), затем незакреплённые (по `CreatedAt`
  убыв.); держим `_pinnedCount`;
- новая запись / touch незакреплённой → удалить со старой позиции (touch), вставить в позицию
  `_pinnedCount` (голова незакреплённой группы);
- touch закреплённой → вставить в позицию 0;
- pin → удалить, вставить в закреплённую группу по `CreatedAt` (бинарный поиск в `[0, _pinnedCount)`),
  `_pinnedCount++`; unpin — зеркально;
- delete → удалить с позиции, поправить `_pinnedCount`.

Честная оговорка: `List.Remove`/`Insert` — это memmove ссылок, формально O(n), но без
компараторов, делегатов и аллокаций: на 100 000 записей это микросекунды против десятков
миллисекунд полной сортировки. **Отклонённая альтернатива** — `LinkedList` с узлом в записи
(истинный O(1)): требует поддерживать указатель границы групп в шести операциях; сложность не
окупается.

Реализация выносится в отдельный internal-класс (`ClipboardHistoryOrder`: список + `_byUuid` +
шесть операций), `ClipboardHistoryService` делегирует ему — это делает порядок **юнит-тестируемым**
без `NativeWindow`, реестра и DPAPI.

### 5.3 Баг `_suppressNext`

`Restore`: `_suppressNext = true` ставится **до** `TrySetText`. Если запись в буфер не удалась,
флаг остаётся взведённым — **следующее настоящее копирование пользователя молча не попадает в
историю**. Фикс: взводить флаг только при `written == true` (или сбрасывать при неудаче).

### Тесты (xUnit, `ClipboardHistoryOrderTests`)

- Property-тест: случайная последовательность из ~1000 операций add/touch/pin/unpin/delete →
  порядок инкрементального класса **равен** эталонной полной сортировке после каждой операции
  (эталон — тот самый `OrderByDescending`, который уходит из продакшена).
- Точечные: touch закреплённой всплывает в голову; pin ложится по своей дате среди закреплённых;
  delete закреплённой уменьшает `_pinnedCount`; `_current` переключается за O(1) (старая запись
  теряет флаг, новая получает).

## 6. Хук-обработчики через `_ui.Post` (№5)

### Проблема

На реальное срабатывание аккорда прямо в колбэке хука (= пока стоит вся клавиатура системы)
выполняются:

- `OnTranslateHotkeyPressed` — **файловый I/O** (`TranslateLog.Log`; антивирус растягивает до
  миллисекунд) и `ShowBalloonTip` на busy-пути;
- `ClipboardHistoryHotkeyPressed → ToggleVisible` — показ окна c `ForegroundActivator.Activate`
  (`AttachThreadInput`) синхронно в колбэке;
- `OnCaseHotkeyPressed` / `OnLayoutConversionHotkeyPressed` — создание `new Thread` (~0,1–1 мс).

Для лаунчера правильный образец уже есть: `OnLauncherHotkeyPressed` только постит работу.

### Решение

Привести четыре подписки в конструкторе `CyrFlipContext` к тому же образцу:

```csharp
_hook.CaseHotkeyPressed              += (_, _) => _ui?.Post(_ => OnCaseHotkeyPressed(null, EventArgs.Empty), null);
_hook.ClipboardHistoryHotkeyPressed  += (_, _) => _ui?.Post(_ => _clipboardHistoryWindow.ToggleVisible(), null);
_hook.LayoutConversionHotkeyPressed  += id     => _ui?.Post(_ => OnLayoutConversionHotkeyPressed(id), null);
_hook.TranslateHotkeyPressed         += id     => _ui?.Post(_ => OnTranslateHotkeyPressed(id), null);
```

Колбэк по-прежнему решает «проглотить клавишу» до возврата — семантика не меняется; вся работа
уезжает на следующий оборот цикла сообщений. Гейт `_busy` при автоповторе работает как раньше
(лишние Post-ы упираются в `CompareExchange` и выходят).

### Приёмка

Ручная: все четыре аккорда работают; busy-балун переводчика показывается; двойное срабатывание
от автоповтора по-прежнему блокируется. Юнит-тестов нет (WinForms-контекст).

## 7. Ротация диагностических логов (№6)

### Проблема

`translate.log` (~6 строк на перевод), `context-menu.log` (строки на каждое открытие меню и
каждый клик — самый болтливый), `launcher.log` — append-only, без ротации. Годы постоянного
использования — десятки мегабайт мусора на диске. `SupportBundle` уже умеет брать хвосты,
но сами файлы никто не усекает.

### Решение

Общий helper вместо трёх одинаковых `Log`-методов — `DiagnosticLog.Append(path, line)`
(lock, `Directory.CreateDirectory`, `File.AppendAllText` — как сейчас), плюс ротация:

- **при первом обращении к файлу за сессию** (static `HashSet<string>` уже-проверенных путей):
  если файл больше **2 МБ** — переписать, оставив хвост **512 КБ**, начиная с границы строки,
  с маркер-строкой в первом ряду (`"[rotated <дата>: older lines dropped]"`) — тот же приём,
  что в `SupportBundle`;
- проверка на каждый Append не нужна: за одну сессию лог на гигабайты не вырастает.

`TranslateLog` / `TextMenuLog` / `LauncherLog` становятся однострочными обёртками над helper-ом
(их публичные сигнатуры и пути к файлам не меняются — `SupportBundle.LogFiles` продолжает
находить те же имена).

### Тесты (xUnit, `DiagnosticLogTests`)

Во временной папке: файл меньше порога — не тронут; больше порога — хвост ≤ 512 КБ, первая
строка — маркер, вторая — целая строка исходного лога (граница строки соблюдена); отсутствующий
файл — просто создаётся. Порог и хвост — параметры helper-а, чтобы тест не писал 2 МБ.

## 8. CaretOverlay: тихий простой (№7)

### Проблема

Фоновый трекер постит `BeginInvoke` на UI-поток ~11 раз в секунду **всегда** — даже когда маркер
скрыт и ничего не изменилось (пустой рабочий стол, консоль, свёрнутые окна). Постоянный тик:
аллокация + пробуждение UI-потока, впустую (батарея/энергия).

### Решение

В `CaretOverlay` запоминать последнее отправленное состояние (`show, x, y, code, caps`);
в `Post` не отправлять, если новое состояние совпадает с последним отправленным
(важнейший случай — «скрыт → скрыт»). При `show == true` с теми же координатами и кодом —
тоже не отправлять.

### Приёмка

Ручная: маркер по-прежнему следует за кареткой, прячется в консоли, меняет код при смене
раскладки, рамка CapsLock появляется/уходит. Проверка простоя — в `Test-LongRun.ps1` косвенно
(снижение фонового CPU не меряем, достаточно отсутствия регрессий).

## 9. Полоска истории: кэш темы и шрифтов (№8)

### Проблема

`ClipboardHistoryWindow.OnPaint` / `DrawCell`: на **каждой** перерисовке — `IsDarkTheme()`
открывает ключ реестра, и создаются/освобождаются ~5 объектов `Font` и набор кистей. Утечки нет
(все под `using`), но это лишняя работа на каждый repaint полоски, которая перерисовывается на
каждое копирование.

### Решение

- `IsDarkTheme`: кэш значения с TTL **2 с** (поле + `Environment.TickCount`); смена темы Windows
  подхватится в пределах 2 с. **Отклонённая альтернатива** — подписка на
  `SystemEvents.UserPreferenceChanged`: точнее, но требует обязательной отписки (сама — источник
  утечки при ошибке) ради события, случающегося раз в месяц.
- Шрифты (`title`, `hotkeyFont`, `big`, `small`, `buttons`): создать один раз (поля), пересоздавать
  в `OnFontChanged`, освобождать в `Dispose`. Кисти зависят от темы — можно оставить per-paint
  (копеечные) или кэшировать парой наборов; решение на усмотрение реализации, приоритет — шрифты.

### Приёмка

Ручная: полоска выглядит как раньше в светлой и тёмной теме; переключение темы Windows
подхватывается (в пределах пары секунд); `Save-SettingsShots.ps1`-эквивалент для полоски не
нужен — визуальная проверка глазами.

## 10. `tools/uitest/Test-LongRun.ps1` (№9)

Пункт «memory stability over 1+ hour» числится в CLAUDE.md как planned — закрываем его
checked-in-инструментом поверх `CyrFlip.UiTest.psm1` (правило: ручные interop-проверки живут
в репозитории, не в scratch-скриптах).

### Что делает

Параметры: `-DurationMinutes` (default 60), `-SampleSeconds` (default 30).

Каждый цикл:

1. Снимает у живого процесса CyrFlip: Private Bytes, `GetGuiResources(GR_GDIOBJECTS)`,
   `GetGuiResources(GR_USEROBJECTS)`, число потоков. Пишет CSV рядом с логами uitest.
2. Раз в N циклов шлёт **аккорд истории** (`Ctrl+Shift+F10` или актуальный из конфига) и
   проверяет появление/скрытие окна истории — это одновременно проверка «хук жив и глотает
   клавишу» для сторожа из §2.
3. Двигает мышь на пиксель (repaint курсора/индикатора) и переключает раскладку окну-жертве
   (Notepad), чтобы жил весь конвейер индикации.

Вердикт в конце:

- **FAIL**, если GDI- или USER-объекты выросли монотонно больше чем на порог (default +200 к
  начальному уровню — рост означает утечку хэндлов);
- **FAIL**, если аккорд истории перестал срабатывать (мёртвый хук);
- Private Bytes — **отчёт без порога** (истории разрешено расти по решению 2026-07-26; порог дал
  бы ложные падения) — числа в CSV, вывод глазами.

Как и остальные скрипты `tools/uitest` — **вне** `dotnet test`/CI: двигает реальную мышь и
крадёт фокус.

## 11. Границы: что НЕ входит (и почему)

| Не делаем | Почему |
| --- | --- |
| Таймаут на кросс-процессные UIA/IAccessible2-вызовы трекера каретки | Сложно (COM-вызов не отменяется штатно; нужен поток-жертва на каждый вызов). Деградация локальна — замирает только маркер — и самоизлечивается, когда целевое приложение отвисает |
| Лимиты, ретеншн или компакция истории буфера | Запрещено принятым решением 2026-07-26 — безлимитность и есть фича; §5 чинит только цену за копирование, не ёмкость |
| Полная переборка всех HGLOBAL-форматов в бэкапе буфера (RTF, HTML и т.д.) | v2 отдельным решением; allow-list из §3 закрывает текст, скриншоты и файлы — практически все реальные потери |
| Переработка `AppendText` окна перевода (квадратичная перерисовка) | Текст ограничен 4000 знаков — на практике незаметно |
| «Пульсовый» детектор снятия хука вместо переустановки по таймеру | Сложнее и капризнее; безусловная переустановка стоит микросекунды (§2) |
| Экономия `StringBuilder`/аллокаций в 150-мс поллинге индикатора | Микрооптимизация без измеримого эффекта |

## 12. Этапы и порядок

Каждый этап: реализация → `dotnet build`/`dotnet test` зелёные и warning-free → отдельный
коммит через `/build` (СБОРКА, `[skip ci]`). Порядок — от самого дешёвого к самому рискованному,
чтобы простые победы не ждали сложных:

1. **История** (§5): `ClipboardHistoryOrder` + `SetCurrent` O(1) + фикс `_suppressNext` +
   `ClipboardHistoryOrderTests`.
2. **SaveBounds** (§4): сохранение в `MouseUp`/`ResizeEnd`.
3. **Post-паттерн** (§6): четыре подписки.
4. **Ротация логов** (§7): `DiagnosticLog` + `DiagnosticLogTests`.
5. **CaretOverlay-простой** (§8) и **кэши полоски** (§9).
6. **Сторож хуков** (§2): `Reinstall` + таймер + балун после трёх неудач.
7. **Бэкап буфера** (§3): `TryGetBytes`/`TrySetBytes` + расширенный `ClipboardBackup` +
   ручная проверка Paint/проводник.
8. **Test-LongRun.ps1** (§10) + часовой прогон на дев-машине; результаты (CSV + вердикт) —
   в отчёт реализации.

После приёмки всех этапов спека переезжает в `PLAN/done/`, а изменившиеся факты (сторож хуков,
форматы бэкапа, ротация логов, новый uitest-скрипт) вносятся в CLAUDE.md одним проходом.
